1. RESUMEN DE LA ARQUITECTURA
================================================================================
Ksmart360 ha evolucionado de un ERP monolítico a una plataforma SaaS Multi-Tenant.
La arquitectura es cliente-servidor desacoplada:

- **Frontend:** Single-Page Application (SPA) en React.
- **Backend:** API RESTful asíncrona construida en FastAPI (Python).
- **Aislamiento Multi-Tenant:** Patrón "Shared Database, Shared Schema". Todas las empresas comparten las mismas tablas, pero los datos se aíslan a nivel lógico mediante la inyección de una llave foránea (`empresa_id`).
- **Monetización:** Motor de suscripciones integrado mediante Webhooks con pasarela de pagos (Wompi).

2. STACK TECNOLÓGICO Y ENTORNOS

- **Backend:** Python 3.10+, FastAPI, Uvicorn, SQLAlchemy (ORM), Passlib (Bcrypt), python-jose (JWT).
- **Frontend:** React 18, Material-UI (MUI v5), Axios, React Router DOM v6, Chart.js.

  - Backend: Render Cloud.

3. MODELO MULTI-TENANT (AISLAMIENTO DE DATOS)
================================================================================
El núcleo del sistema reside en `models.py` a través de la clase abstracta `TenantMixin`.

- **Regla de Arquitectura:** TODA tabla operativa (`Ventas`, `Productos`, `Compras`, etc.) HEREDA de `TenantMixin`. Esto inyecta automáticamente la columna `empresa_id`.
- **Regla de Desarrollo (Backend):** Nunca se deben ejecutar consultas globales (ej: `db.query(Venta).all()`). Todas las operaciones en `crud.py` exigen el paso del parámetro `empresa_id` extraído del token JWT del usuario solicitante, aplicando `.filter(Model.empresa_id == empresa_id)`.
- **Tablas Globales:** Solo `Empresa`, `Role`, y `Modulo` carecen de `empresa_id`.

================================================================================
4. ESTRUCTURA DEL BACKEND (FastAPI)
================================================================================
El código backend se concentra en la carpeta raíz (o `/backend`):
- `main.py`: Punto de entrada. Define routers, dependencias de seguridad, middlewares CORS y Webhooks de pago.
- `models.py`: Definición declarativa de SQLAlchemy. Contiene la estructura de la base de datos y el `TenantMixin`.
- `schemas.py`: Modelos Pydantic para validación estricta de request/response y serialización.
- `crud.py`: Capa de abstracción de base de datos. Contiene toda la lógica de negocio compleja (Kardex, Lotes de Producción, Corte de Caja).
- `database.py`: Gestión de conexión SQLAlchemy y motor de migraciones customizado.

================================================================================
5. ESTRUCTURA DEL FRONTEND (React SPA)
================================================================================
- `App.js`: Corazón del enrutamiento. Gestiona el estado global (token, roles, módulos permitidos) y renderiza el Layout (Drawer/AppBar) o la pantalla de bloqueo (Suscripción Expirada).
- `src/components/`: Contiene los módulos funcionales (`Ventas.js`, `Inventario.js`, `Dashboard.js`). Utiliza un enfoque de modales intensivos (MUI Dialogs) para mantener al usuario en contexto.
- `src/api.js`: Configuración global de Axios.
  - **Interceptor Request:** Inyecta `Authorization: Bearer {token}`.
  - **Manejo de Errores (402):** El estado HTTP 402 (Payment Required) se gestiona en la capa de UI para redirigir al componente `<SuscripcionExpirada />`.

================================================================================
6. FLUJO DE AUTENTICACIÓN Y AUTORIZACIÓN
================================================================================
Seguridad basada en JWT sin estado (Stateless):
1. **Login:** `POST /token` valida credenciales y devuelve un JWT. El payload incluye `sub` (username), `empresa_id`, `role`, y `modules`.
2. **Jerarquía de Guardias (Dependencies en `main.py`):**
   - `get_current_user`: Valida la firma del JWT.
   - `get_current_active_user`: **[Vital]** Valida que `empresa.is_active == True`. Si el plan es "trial", verifica `trial_ends_at` contra UTC actual. Lanza 402 si expiró.
   - `get_current_admin_user`: Exige rol "Admin".
   - `get_current_superadmin_user`: Acceso maestro. Exige rol "Admin" Y `empresa_id == 1`.
3. **Impersonación (Login As):** El SuperAdmin puede generar un token temporal con `is_impersonated: True` y el `empresa_id` de un cliente para brindar soporte directo.

================================================================================
7. MOTOR DE PAGOS Y FACTURACIÓN SAAS (Wompi)
================================================================================
El sistema se auto-monetiza mediante integración con Bancolombia/Wompi.
- **Frontend (`WompiButton.js`):** Instancia el `WidgetCheckout` de Wompi. Exige configuración estricta de firma en formato `{ integrity: "hash" }`.
- **Backend (`/wompi/generar-hash`):** Genera firma HMAC SHA-256 usando `WOMPI_INTEGRITY_SECRET` para prevenir manipulación de precios.
- **Webhook (`/webhooks/wompi`):**
  - Verifica firmas criptográficas entrantes de Wompi.
  - Implementa **Idempotencia** (verifica `bold_tx_id` en `registros_pagos`) para evitar sumar meses dobles ante reintentos de la pasarela.
  - Si es exitoso, actualiza `plan_type` a "premium", suma `dias_duracion` a `trial_ends_at` y activa el tenant automáticamente.

================================================================================
8. SISTEMA DE MIGRACIONES (Custom)
================================================================================
El proyecto NO utiliza Alembic para evitar dependencias complejas en el despliegue.
- La lógica reside al final de `database.py` en `run_migrations()`.
- Utiliza la tabla `_schema_meta` para rastrear migraciones ejecutadas.
- Al iniciar la app (`@app.on_event("startup")`), evalúa si hay nuevas columnas o tablas (Ej: Inyección de columnas de Wompi) y ejecuta los `ALTER TABLE` dinámicamente si es seguro (usando SQLite Pragmas o Information Schema de Postgres).

================================================================================
9. MÓDULOS CRÍTICOS Y LÓGICA DE NEGOCIO
================================================================================
- **Kardex y Costo Promedio:** El inventario (`stock_actual`) es un valor derivado. La verdad absoluta reside en `inventory_movements` (Append-Only). El Kardex recalcula saldos y costo promedio ponderado al vuelo.
- **Producción (BOM):** La transformación de materias primas a productos terminados ocurre en `LoteProduccion`. El descuento de insumos solo se ejecuta al cambiar el estado a "Confirmado".
- **Corte de Caja:** Entidad inmutable que realiza un snapshot cruzando ingresos en efectivo de la tabla `Ventas`, restando `Gastos` y comparando con `efectivo_fisico` para arrojar diferencias.
